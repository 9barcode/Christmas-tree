# BM v2 — 광고로 장식을 모으는 트리 꾸미기

기준일: 2026-10-19 (Asia/Seoul)

상태: **사용자 확정 BM 및 구현 전환 명세. 이 문서 커밋은 실행 코드 변경이 아니다.**

본 문서의 신규 BM은 기존 출석·결석·연속 출석 기획보다 우선한다. 운영 적용은 서버·프론트엔드·광고 설정·프로모션 조건을 함께 전환한 뒤 진행한다. 플랫폼 승인 완료를 의미하지 않는다.

## 1. 확정된 규칙

| 항목 | 신규 규칙 |
| --- | --- |
| 기본 슬롯 | 1번은 초록 트리 기본 제공 |
| 추가 슬롯 | 2~5번은 기본 잠금. 사용자가 원하는 슬롯을 선택하고 **리워드형 광고** 완료 후 해당 슬롯만 영구 해제 |
| 슬롯 해제 순서 | 앞 슬롯의 출석·장식 수와 관계없이 선택 가능 |
| 장식 획득 | **일반 전면형 광고** 정상 종료 후 선택한 트리에 장식 1개 추가 |
| 일일 장식 한도 | **사용자 전체·모든 슬롯·모든 회차 합산 10개**. 슬롯마다 10개가 아님 |
| 출석·결석 | 폐지. 연속 방문이나 결석에 따른 종료·초기화·부분 정산 없음 |
| 트리 완성 | 장식 30개를 채우고 꾸미기를 완성하면 30원 상당의 교환 대기 잔액 적립 |
| 토스포인트 교환 | 교환 시 **일반 전면형 광고** 정상 종료 후 서버를 통해 토스포인트 지급 요청 |
| 트리 수·색상 | 최대 5개. 1번 초록 고정, 추가 트리는 기존 5색 무작위이며 생성 후 유지 |
| 장식 구성 | 선물 4 + 미니카 1 + 인형 1 + 오너먼트 22 + 전구 줄 1 + 별 1 = 30개 유지 |

일일 10개는 **장식 획득 수**의 한도다. 슬롯 해제와 포인트 교환 광고는 장식을 지급하지 않으며 이 10개에서 차감하지 않는 것을 구현 기준으로 삼는다. 한도 날짜는 기존 앱과 동일하게 한국시간 자정에 바뀐다. 운영상 교환 별도 한도는 프로모션 조건과 함께 확정해야 한다.

30원은 계좌로 지급하는 현금이 아니다. 앱 내 교환 대기 가치와 실제 토스포인트 지급을 별도 원장으로 관리한다. 기본 전환 목표는 30원 상당 → 30 토스포인트이며 실제 운영은 승인된 프로모션 조건을 따른다.

## 2. 광고 유형은 용도별로 분리

| 목적 | 광고 유형 | 클라이언트 처리 기준 |
| --- | --- | --- |
| 슬롯 영구 해제 | Rewarded | SDK의 실제 `userEarnedReward` 확인. 광고 화면 종료 후 해제 결과 반영 |
| 장식 1개 획득 | Interstitial | 광고 표시 후 실제 `dismissed`로 정상 종료된 흐름을 확인 |
| 토스포인트 교환 | Interstitial | 광고 표시 후 실제 `dismissed`로 정상 종료된 흐름을 확인한 뒤 교환 요청 |

카드 대장간 참조:
- 저장소: `bluehawhy/card-forge`
- 확인 커밋: `9c66b957226e2d8bef4295d6c275980826ac26c2`
- 파일: `src/services/rewardedAdService.ts`
- `isRewardedAdSuccess`는 현재 `dismissed === true`를 판정한다. 이름에 Rewarded가 남아 있지만 일반 전면광고 종료를 처리하는 호환 구조다.

트리에서는 이 이름 혼용을 그대로 복제하지 않는다. `unlock-slot` / `earn-decoration` / `exchange-points` 목적을 구분하고 일반 전면형 결과에 `rewarded: true`나 가짜 `userEarnedReward`를 만들지 않는다. 일반 전면형을 리워드 광고의 끝까지 시청한 것으로 설명하지 않는다.

광고 미지원·설정 누락·로드 실패·표시 실패·표시 전 종료·타임아웃에는 슬롯 해제, 장식 증가, 지급 요청을 진행하지 않는다. 광고 생략/bypass를 성공으로 취급하지 않는다. 광고 클릭은 지급 조건이 아니다. 광고를 연속 자동 재생하지 않고 사용자 동작마다 한 번만 호출한다.

현재 `REWARDED_AD_GROUP_ID_1`~`5`를 일반 전면형 ID라고 간주해서 재사용하지 않는다. 콘솔의 실제 광고 유형에 맞게 슬롯 해제용 리워드 ID와 장식/교환용 전면형 ID를 별도로 구성한다. 광고 ID 개수·슬롯별 분할은 운영 설정으로 관리한다.

## 3. 일일 한도와 완성 보상

- 한도 키는 인증된 사용자와 한국시간 날짜다. 앱 데이터 삭제, 기기 변경, 슬롯 변경, 트리 재시작으로 한도가 복구되지 않는다.
- 광고 호출 전 서버가 슬롯 잠금 여부, 장식 수, 당일 잔여 횟수를 확인하고 단일 사용 요청 ID를 예약한다.
- 같은 사용자의 동시 요청에서도 장식 11개째를 허용하지 않도록 서버 트랜잭션 또는 조건부 갱신으로 제어한다.
- 실패한 광고는 획득 횟수로 세지 않는다. 동일 요청 재전송은 기존 결과를 돌려주며 장식을 다시 지급하지 않는다.
- 장식 획득과 일일 횟수 증가는 같은 서버 처리 단위에서 확정한다.
- 30번째는 별을 해금한다. 완성 처리는 트리·회차별 한 번만 허용한다. 배치 변경이나 공유·재접속으로 30원을 반복 적립하지 않는다.
- 모든 획득을 한 트리에 사용하면 최소 3일에 30개를 모을 수 있다. 여러 트리에 나누면 개별 트리 완성 시점은 늦어지며 획득분은 유지된다.
- 최종 배치를 마친 뒤 `트리 완성하기`로 완료를 확정하는 UI를 제안한다. 버튼의 정확한 위치·문구는 구현 시 기존 디자인에 맞춰 검증한다.

클라이언트의 SDK 이벤트 전달 자체는 서버가 광고 네트워크 시청을 독립 검증했다는 증거가 아니다. 서버 발급 요청 ID·사용자·목적·슬롯·광고 ID를 결합하고 재사용을 차단한다. 광고 공급자가 제공하는 서버 검증 수단이 있다면 추가 연동한다. 클라이언트의 완료 횟수·금액을 그대로 신뢰하지 않는다.

## 4. 적립과 교환은 별개

1. 트리 완성 확정 시 서버가 해당 회차에 30원 상당의 원장 항목을 한 번만 생성한다.
2. 교환을 누르면 서버가 지급 가능한 잔액과 교환 요청 ID를 예약한다.
3. 전면형 광고가 정상 종료되면 그 요청 ID로 교환을 요청한다.
4. 서버가 새 BM용으로 승인·설정한 프로모션을 호출한다.
5. 지급 성공이 확인된 경우에만 교환 확정으로 기록한다. 확인 중인 요청은 다시 광고를 요구하거나 중복 지급하지 않고 결과 조회로 복구한다.

광고 실패 시 예약을 해제한다. 지급 결과가 불명확하면 pending으로 보존한다. 명확한 지급 실패와 단순 응답 유실을 구분한다. 클라이언트 버튼이나 localStorage만으로 잔액을 증감하지 않는다.

교환 최소 단위, 여러 완성분의 합산 교환, 일일 교환 상한, 프로모션 예산 소진 시 안내는 운영 상세 규칙으로 별도 확정한다. 장식 일일 10개 한도와 교환 한도는 다른 이름·필드로 관리한다.

## 5. 유지할 UI와 교체할 UI

유지:
- 실내 배경, 불·눈 효과, 기존 트리·화분·장식·그림 버튼 디자인.
- 트리·별·전구의 고정 배치와 나머지 소품의 기존 드래그 배치.
- 슬롯 썸네일과 실제 트리 상태의 동기화, 사진 저장·공유.
- 임시 날짜 테스트 도구는 별도 삭제 요청 전까지 유지. 새 BM에서는 한국시간 일일 한도 테스트에 활용.

교체:
- 2~5번 미해제 슬롯은 잠금으로 표시하고 선택 시 슬롯 해제용 리워드 광고 진입.
- `출석하고 트리 꾸미기` → 장식 획득 CTA. 전면광고 표시 사실을 사용 전에 명확히 안내.
- 사용자 전체의 `오늘 획득 0/10` 또는 `오늘 남은 장식 10개` 표시.
- 출석표·루돌프 출석 도장·결석 안내는 장식 획득/완성/교환 내역으로 교체. 트리 장식 에셋인 순록은 제거하지 않음.
- 기존 누적 1+2+…+30 보상, 결석 부분 정산, 출석 15/30일 프로모션을 새 BM의 획득·완성 보상 조건으로 사용하지 않음.
- 안내 팝업은 새 규칙으로 교체하되 별도 불필요한 팝업은 추가하지 않음.

완성 트리의 사진 저장·공유는 포인트 교환 성공과 분리하는 것을 구현 방향으로 삼는다.

## 7. 기존 이용자 이관 — 실행 전 확정 필요

- 기존 트리 색상·장식 수·배치·사진은 자동으로 지우지 않는다.
- 이미 생성된 2~5번 트리를 잠그고 접근을 막을지, 기존 사용자에게는 해제로 유지할지는 별도 이관 결정이 필요하다. 신규 사용자 기본 잠금 규칙과 구분한다.
- 구 BM의 미수령·지급 확인 중 보상은 새 BM의 30원으로 덮어쓰지 않는다. 기존 원장과 지급 재시도 요청을 보존한다.
- 기존 30개 완성 트리의 신규 30원 적립 대상 여부는 별도 확정한다. 배포 순간 일괄 소급 지급하거나 기존 지급과 중복 적립하지 않는다.
- 트리 재시작 허용 시점, 같은 슬롯의 반복 완성 보상 여부는 기존 출석 정산·지급 완료 조건을 그대로 가져오지 않고 새 BM 기준으로 확정한다.

## 8. 검증 및 적용 순서

1. 이 BM 명세 확정 및 운영 상세·기존 사용자 이관 규칙 결정.
2. 신규 데이터 모델과 마이그레이션, 서버 일일 합산 한도·요청 중복 방지 테스트.
3. 목적별 광고 처리 구현. 광고 실패, 중복 콜백, 표시 없는 종료, 빠른 연속 클릭 검증.
4. 프론트엔드 교체 및 기존 에셋/드래그/슬롯 저장 회귀 검증.
5. 완성 적립·교환 지급/조회/실패 복구 구현 및 테스트용 프로모션으로 검증.
6. 승인된 광고 그룹·프로모션 설정과 이관 절차를 확인하고 운영 전환.

필수 확인: 전 슬롯 합산 10개, 11번째 거절, KST 자정 재개, 결석 후 보존, 장식 30개 상한, 슬롯 해제 실패 시 잠금 유지, 영구 해제 재접속 유지, 회차별 30원 중복 적립 차단, 같은 교환 요청 중복 지급 차단, 클라이언트 캐시 삭제/다른 기기에서도 서버 한도 유지.

## 9. 공식 문서와 운영 확인

### 배너 지면 추가

로딩 화면에 텍스트 중심 리스트형 1개와 이미지 피드형 1개, 홈 장면 바깥 하단에 단일 배너 지면을 둔다. 트리 꾸미기 영역과 저장·공유 사진에는 포함하지 않는다. 배너 클릭·노출에는 보상을 연결하지 않고 장식 일일 한도에도 포함하지 않는다. 상세 배치와 운영 설정은 [배너 지면 문서](banner-placements.md)를 따른다. 이 배너 구현과 별개로 BM v2의 획득·정산·교환 실행 코드는 아직 이전 버전이다.

공식 문서는 Interstitial과 Rewarded의 이벤트 흐름을 구분한다. 일반 전면형의 `dismissed`는 리워드형의 `userEarnedReward`와 같지 않다. 카드 대장간의 구현 사례가 이 트리 BM에 대한 플랫폼 승인을 대신하지 않는다.

장식/완성과 토스포인트 지급을 연결하는 신규 구조와 자체 적립 잔액 운영은 실제 미니앱 분류 및 프로모션 심사 조건을 확인해야 한다. 기존 출석 프로모션 코드를 다른 지급 조건에 그대로 사용하지 않는다. 문서에 정의한 자체 잔액을 현금 지급 보장으로 안내하지 않는다.
